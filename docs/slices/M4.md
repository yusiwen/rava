# M4 slice detail — resources, jars and the non-web Boot application

Per-slice record for M4. `PROJECT.md` § Slices owns the status and the one-line
description; this file owns what each slice delivered, where it stops and the evidence
behind it. Every entry is recorded from the slice's own acceptance run on 2026-11-26.

## M4.1 — Classpath resources: directory/jar lookup and enumeration, `ClassLoader`/`Class` resource natives, `file:`/`jar:` URL streams — 2026-11-26

**Acceptance.** `cargo test -p rava-cli --test resources` — exit 0.

**Delivered.** `ClassSource` gains `read_resource`/`resource_urls`/`resource_names`: `DirectorySource` returns `file:` URLs and walks files under a prefix, `JarSource` returns absolute `jar:file:...!/entry` URLs, and `ClassPathSource` preserves classpath order. `Shared`/`ClassTable` look resources up parent-first through the loader chain; `ClassLoader.getResource(s)`, the four system forms and `Class.getResource(AsStream)` now call it. A side table keyed by `ObjRef` holds URL components, stream bytes/cursors, `ByteArrayOutputStream` buffers and connection state; `Shared::roots` reports its keys and the no-lock probe covers it. The new `java.net.URL`/`URLConnection`/`java.io.InputStream` natives open `file:` and `jar:` resources with no network transport; `URL` supports constructors, component queries, equality, `openStream`/`openConnection`, and `InputStream` returns unsigned 0..255 bytes and `-1` at EOF. Supporting gates added `ByteArrayOutputStream`/`OutputStream.flush`, mutable `Iterator.remove`, `URLDecoder.decode`, `Properties.load` and `Arrays.stream(Object[])` because the new resource path exposed them. The committed `crates/cli/tests/fixtures/resources/` directory/jar fixture and `cargo test -p rava-cli --test resources` (2 tests) assert directory-first and reversed classpath order, both URL protocols, both payloads, missing-resource null and stream EOF; `ResourceProbe` stdout is exact. `cargo test --workspace` passes 501 tests; `RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context` prints `hello\n`; `RAVA_C2_ACCEPTANCE=1 cargo test -p rava-cli --test c2_gate` passes 2; `compat check`/`metadata --check` and fmt/clippy exit 0. Limits: no network, no URLConnection headers/content type/dates, no nested jars, and no custom `URLStreamHandler`; `-jar`/nested/Boot are later M4 slices.

**Boundary.** a resource is a second view of a `ClassSource`, not a second source
model. `read_resource` returns bytes, `resource_urls` returns external forms and
`resource_names` enumerates a prefix; a directory uses `file:/<absolute-path>` and a jar
uses `jar:file:/<absolute-jar>!/<entry>`. `Shared::resource_urls`/`read_resource` walk the
loader chain parent-first (bootstrap, then application/child), so `ClassLoader.getResource`
returns the first URL, `getResources` every URL in that order and `getResourceAsStream`
the first bytes; `Class.getResource` resolves `/absolute` at the loader root and a
relative name against the class's package. The URL, connection, input-stream and
`ByteArrayOutputStream` state is Rust text/bytes in an `ObjRef`-keyed side table, not a
new heap shape; `Shared::roots` reports the keys and the no-lock probe covers the lock.
Only `file:` and `jar:file:...!/entry` open (no network), `URLConnection` has no headers,
content type or dates, `URL.getLastModified` is 0, and nested jars/custom handlers are
later M4 slices. `InputStream.read()` returns the unsigned 0..255 byte and -1 at EOF.
The `crates/cli/tests/fixtures/resources/` directory/jar fixture and
`cargo test -p rava-cli --test resources` (2 tests) assert both classpath orders; the
workspace is 501 tests and the Spring/C2/compat gates remain green.

## M4.2 — `ServiceLoader` over `META-INF/services`, lazy provider iteration and typed configuration errors — 2026-11-26

**Acceptance.** `cargo test -p rava-cli --test service_loader` — exit 0.

**Delivered.** `ClassSource::read_resources` returns every copy of a resource: its default wraps `read_resource`, `ClassPathSource` concatenates every directory/jar entry in classpath order, and `ClassTable`/`Shared::read_resources` walk the loader chain parent-first while `read_resource` keeps first-match. A new `ObjRef`-keyed `ServiceState` table in `Shared` holds each `java.util.ServiceLoader`'s service `ClassId`, defining `LoaderId`, provider `ClassId`s and iterator cursor; `SharedLock::ServiceLoaders` and its no-lock probe cover the lock, and the table owns no Java references so it adds no roots. `rava_interp::service_loader` implements `load(Class)` (application loader), `load(Class, ClassLoader)` (null selects bootstrap), `iterator()` and overrides `java/util/Iterator.hasNext`/`next` with a fallback to the VM snapshot natives; `load` reads `META-INF/services/<binary-name>` with comments/trimming/blank lines and file order, normalizes each dotted provider name to its internal name before `load_class` so the provider keeps the ordinary class identity, loads and `named_assignable`-checks every provider, rejects primitive/array service classes and names a missing or invalid provider in a typed `VmError::Native`; `next` allocates the provider and runs `<init>()V` through `run_instance_method`, so `<clinit>` and constructors happen on first use. The committed release-17 `crates/cli/tests/fixtures/service_loader/` fixture puts HelloGreeter's provider file in the directory and WorldGreeter's in `providers.jar`; `cargo test -p rava-cli --test service_loader` (9 tests) asserts both classpath orders, the explicit and null loader overloads, the empty missing service, the provider's internal-name identity, the typed errors, and `clinit:`/`init:` output after `after-hasNext` to prove laziness. `cargo test --workspace` passes 514 tests; `RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context` prints `hello\n`; `RAVA_C2_ACCEPTANCE=1 cargo test -p rava-cli --test c2_gate` passes 2; `compat check`/`metadata --check` and fmt/clippy exit 0. Limits: one provider name per line, no module layer/`loadInstalled`, no `Provider`/`stream`/`findFirst`, no `ServiceConfigurationError` object; `-jar`/nested/Boot are later M4 slices.

**Boundary.** a service loader is ordinary VM state, not a new heap shape. `ClassSource`
gains `read_resources`, whose default wraps `read_resource` and whose `ClassPathSource`
override returns every matching entry in classpath order; `ClassTable`/`Shared::read_resources`
walk the loader chain parent-first and concatenate, while `read_resource` keeps its
first-match behavior. The `ServiceLoader` object and its iterator are ordinary C1-class
instances; their service `ClassId`, defining `LoaderId`, provider `ClassId`s and cursor
live in an `ObjRef`-keyed `ServiceState` table with a `SharedLock::ServiceLoaders` no-lock
probe. That state owns no Java references, so `Shared::roots` does not report its keys.
`rava_interp::service_loader` parses `META-INF/services/<binary-name>` (one provider per
line, `#` comments, trimming, blank lines, file order), normalizes each dotted name to the
internal `a/b/C` form before loading so the provider has the same `(loader, name)`
identity as `ldc`/`Class.forName`/`ClassLoader.loadClass`, loads every provider through
the selected loader, checks `named_assignable` and rejects primitive/array service classes
with a typed `VmError::Native` naming the provider. `load` constructs no provider; it only
loads and validates the provider classes. `iterator` allocates a snapshot
`java.util.Iterator`; `hasNext` reads the cursor;
`next` allocates the provider and runs `<init>()V` through `run_instance_method`, so
`<clinit>` and constructor output happen on first use. The interp module overrides the
`Iterator.hasNext`/`next` registry entries and delegates every ordinary iterator to the
VM snapshot natives. Limits: one provider name per line, no module layer/`loadInstalled`,
no `Provider`/`stream`/`findFirst`, no `ServiceConfigurationError` object, and no `-jar`
or nested-jar loading; those remain M4.3/M4.4.

## M4.3 — Executable-jar launch: manifest parsing, `Main-Class`, `Class-Path` and `rava -jar` — 2026-11-26

**Acceptance.** `cargo test -p rava-cli --test jar_launch` — exit 0.

**Delivered.** `crates/cli/src/jar.rs` adds the launcher's manifest reader: it reads `META-INF/MANIFEST.MF` through the existing `JarSource`, accepts `\r\n`/`\n`, joins a value continued on a line beginning with one space, matches `Main-Class`/`Class-Path` names case-insensitively, preserves values, and returns a typed `ManifestError::Malformed { line, reason }` that names the 1-based line; `Manifest::main_class` returns `None` for a missing or empty value and `class_path` splits the whitespace-separated entries in manifest order. `rava -jar <file> [--stdlib <dir>] [--] [args...]` is dispatched from `main.rs` and builds the classpath as the executable jar first, then each `Class-Path` entry resolved relative to the executable jar's parent; plain relative/absolute paths and `file:` URLs (including `file:///...`, a named authority and percent escapes) are accepted, and an entry that does not exist or cannot open is skipped as the JDK does while the executable jar is fatal. `Main-Class` is required (missing/empty is exit 1), a missing/unreadable/malformed jar is exit 1, and missing `--stdlib` values/unknown options/missing jar paths are exit 2. `run::Options` is `pub(crate)` and a new `run::execute_with` shares the loader, native registration, `String[]` allocation and `main([Ljava/lang/String;)V` call with `rava run`, whose contract is unchanged. The committed `crates/cli/tests/fixtures/jar_launch/` fixture has `app.jar` (`Main-Class: demo.JarMain`, `Class-Path: lib/helper.jar`, `data.txt`, class files, source and rebuild README) and `lib/helper.jar` (`demo.Helper`); `cargo test -p rava-cli --test jar_launch` (13 tests) asserts the exact three-line stdout (`jar:hello`, `helper:helper`, `resource:jar-resource`), ordered program arguments, `--` literal arguments, an explicit `--stdlib` from another directory, the default stdlib from the repository root, missing jar/non-jar/missing manifest/missing or empty `Main-Class`/malformed manifest exit 1, unusable Class-Path entries skipped with exit 0, and the three usage errors exit 2. Ten new unit tests cover wrapping, CRLF/LF, case-insensitive keys, missing/empty `Main-Class`, per-entry sections, a missing final newline, malformed headers and path/URL resolution; `cargo test --workspace` passes 537 tests; `RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context` prints `hello\n`; `RAVA_C2_ACCEPTANCE=1 cargo test -p rava-cli --test c2_gate` passes 2; `compat check`/`metadata --check` and fmt/clippy exit 0. Limits: flat jars only — no nested jars/`BOOT-INF`/Boot launcher (M4.4), no `URLClassLoader`, and only `Main-Class`/`Class-Path` are read from the manifest.

**Boundary.** `-jar` is a launcher over the existing classpath source, not a second
class loader. `crates/cli/src/jar.rs` owns the manifest reader and resolves the
executable jar plus its `Class-Path` entries into the same `ClassPathSource` `rava run`
uses; `run::execute_with` shares the application loader, native registration, `String[]`
allocation and `main` invocation, so the launch contract cannot drift. The reader keeps
only the main-attributes section (the first blank line ends it), matches names
case-insensitively, joins continuation lines and reports a malformed header with its
1-based line; `Main-Class` must be present and non-empty. The executable jar is entry
zero and a `Class-Path` entry it cannot open is skipped (as the JDK's application
launcher does), because a helper jar changes reachability, not whether the program
starts. This is the flat executable-jar path; M4.4 adds the Boot nested layout below
without changing it.

## M4.4 — Boot nested-jar layout: `BOOT-INF/classes`, `BOOT-INF/lib/*.jar`, nested `jar:` URLs and launcher classpath — 2026-11-26

**Acceptance.** `cargo test -p rava-cli --test nested_jars` — exit 0.

**Delivered.** `crates/vm/src/boot.rs` adds `BootJarSource` over the existing `JarSource`: `is_boot`/`from_jar` recognise a `BOOT-INF/classes/` or `BOOT-INF/lib/` entry and return `None` for a flat jar; each `BOOT-INF/lib/*.jar` is indexed with the new `JarSource::from_bytes` (no file needed) and searched in lexical entry-name order; a malformed nested entry is the typed `VmError::BootEntry { entry, detail }`; `read`/`read_resource` search the classes root then the nested jars, `read_resources` keeps every copy in that order, `resource_names` strips `BOOT-INF/classes/`, and `resource_urls` emits `jar:file:<outer-abs>!/BOOT-INF/classes!/<name>` and `jar:file:<outer-abs>!/BOOT-INF/lib/<lib>.jar!/<name>` with the M4.1 percent-encoding. `resources.rs::read_jar_url` keeps a one-`!/` URL flat and resolves the two-`!/` Boot forms through `BootJarSource`, so `URL.getPath`/`getFile`/`toString`/`openStream` and `new URL(externalForm)` work. `run::execute_with` now takes `Arc<dyn ClassSource>`; `rava -jar` detects the Boot layout before the flat path: a `Main-Class` that is not a Boot launcher runs directly, and a Boot-launcher `Main-Class` (or a missing one) requires a non-empty `Start-Class` (exit 1 when missing) that is substituted for it (documented substitution; no Boot loader classes are loaded or run), and deliberately ignores a Boot layout's manifest `Class-Path` because Boot builds its classpath from `BOOT-INF` (tested). The committed `crates/cli/tests/fixtures/nested_jars/` fixture has `fat.jar` (`Main-Class: org.springframework.boot.loader.launch.JarLauncher`, `Start-Class: demo.NestedMain`, `BOOT-INF/classes/demo/NestedMain.class`, `BOOT-INF/classes/outer.txt`, `BOOT-INF/lib/demo-helper.jar`) and the nested helper jar (`demo/NestedHelper`, `demo/InnerGreeter`, `inner.txt`, `META-INF/services/demo.Greeter`); `cargo test -p rava-cli --test nested_jars` (7 tests) asserts the exact 16-line stdout, nested class loading and the shared application-loader identity, both Boot URL forms through `getResources`/`URL.openStream`/`new URL(...)`, the nested `ServiceLoader`, a Boot launcher without `Start-Class` exiting 1, an ordinary `Main-Class` in a Boot layout running without `Start-Class`, a malformed nested jar naming `BOOT-INF/lib/broken.jar`, an ignored Boot `Class-Path`, and a flat jar still on the flat path. Five `boot.rs` unit tests plus `JarSource::from_bytes` stored/DEFLATE tests cover detection, order, names, URLs and the typed error; `cargo test --workspace` passes 552 tests; `RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context` asserts and passes `hello\n`; `RAVA_C2_ACCEPTANCE=1 cargo test -p rava-cli --test c2_gate` passes 2; `compat check`/`metadata --check` and fmt/clippy exit 0. Limits: no Boot loader classes/`URLClassLoader`, no `loader.path`/exec, no nested-jar `Class-Path`, lexical (not central-directory) nested-jar order, eager in-memory indexing of every nested jar, and `rava run --cp` does not treat a Boot jar as a Boot layout.

**Boundary.** a Boot executable jar is a `ClassSource`, not a new loader.
`BootJarSource` indexes the outer `BOOT-INF/classes/` tree and each `BOOT-INF/lib/*.jar`
(in lexical entry-name order) through the existing `JarSource`; a nested jar is built with
`JarSource::from_bytes` and a malformed entry is `VmError::BootEntry` naming the entry.
`read`/`read_resource` search the classes root first and then the nested jars,
`read_resources` returns every copy in that order, `resource_names` strips the classes
prefix, and `resource_urls` emits `jar:file:<outer>!/BOOT-INF/classes!/<name>` and
`jar:file:<outer>!/BOOT-INF/lib/<lib>.jar!/<name>`; `read_jar_url` resolves both through
`BootJarSource` and keeps a one-`!/` URL flat. Application classes keep the ordinary
`(loader, name)` identity and the ordinary resource APIs. `-jar` detects the layout: a
`Main-Class` that is not a Boot launcher runs directly, and otherwise a non-empty
`Start-Class` is required and substituted for the launcher; the pinned jars carry no Boot
loader classes, so no `JarLauncher` or `URLClassLoader` runs. A Boot layout's
`Class-Path` is ignored because Boot builds its own classpath from `BOOT-INF`;
`loader.path`, exec and a nested jar's own `Class-Path` are not implemented.
`rava run --cp` still treats every jar entry as a flat jar; only `-jar` selects the Boot
source.

## M4.5 — Non-web Boot application gate: real `SpringApplication` with `WebApplicationType.NONE` on the pinned jars — 2026-11-26

**Acceptance.** `RAVA_BOOT_ACCEPTANCE=1 cargo test -p rava-cli --test boot_nonweb` — exit 0.

**Delivered.** `crates/cli/tests/fixtures/boot_nonweb/` is a committed, real Boot application (`@SpringBootConfiguration`, `SpringApplication` with `WebApplicationType.NONE`, one `@Bean ApplicationRunner` printing `boot:started`); the source and its `javac --release 17` class file are committed so CI needs no JDK. `crates/cli/tests/boot_nonweb.rs` (3 tests) asserts the pinned classpath has all 35 jars, that the fixture class is committed, and that the real `rava-cli run demo.BootNonWeb --stdlib <c1> --cp <fixture + all 35 jars>` exits 0 with `boot:started` on stdout; the child runs under `ulimit -s 65536` and is killed after 180s so a deadlock fails instead of hanging. Ordinary `cargo test` skips when `compat/jars` is absent, while `RAVA_BOOT_ACCEPTANCE=1` makes that a failure. The startup chain fixed general VM/library gaps only, each observed on the way: `LinkedBlockingQueue` (slf4j's substitute provider), `InheritableThreadLocal`, the `java.time` formatter/instant/zone/clock/duration surface (logback and Boot startup timing), `String.format`/`String.getBytes`/case/subSequence/`chars` with an `IntStream` tag, `OutputStream`/`PrintStream.write`, `EnumSet`/`EnumMap`/`Collections`/`Map`/`List`/`Set` equality and default methods, `MethodHandles`-style record `equals`/`toString`, `LambdaMetafactory.altMetafactory`'s real argument order (sam/impl/instantiated/flags), `Class` predicates/enclosing/declaring/array type/parameter annotations, `java.beans` descriptors with virtual `setReadMethod`/`setWriteMethod`, `java.io.File`/`URI`/`InputStreamReader`/`BufferedReader`/`Properties`, `java.lang.management.RuntimeMXBean`, `java.nio.charset.Charset`, `BigInteger`, `SecureRandom`, `java.util.BitSet`, and interface-default/interface-hierarchy dispatch (including a `run_method` heap-lock re-entry deadlock that was found and fixed). `boot:started` was observed with exit 0; `cargo test --workspace` passes 555 tests; `RAVA_SPRING_ACCEPTANCE=1 ... spring_context` prints `hello` and exits 0; `RAVA_C2_ACCEPTANCE=1 ... c2_gate` exits 0; `compat check`/`metadata --check` and fmt/clippy exit 0.

**Boundary.** The gate starts a real Boot context, not the whole auto-configuration
graph. The fixture is `@SpringBootConfiguration` + a `@Bean ApplicationRunner` and does not
carry `@EnableAutoConfiguration`: the full `@SpringBootApplication` path then activates
Jackson, SSL, HTTP message converters and task-executor auto-configurations whose optional
dependencies and bean graphs are C3 targets beyond M4. The fixture still runs the real
`SpringApplication` lifecycle with `WebApplicationType.NONE`, registers a real bean
definition, creates the annotation context, and calls the runner; the assertion is that
`boot:started` is printed and the process exits 0. The Boot startup work is supported by
general natives, not Boot special cases: JDK classes the pinned libraries call are
implemented from their observed behavior, and the M4.5 sub-boundaries are the
single-threaded VM (no `Thread.start`, no executor; `CountDownLatch.await` and
`LinkedBlockingQueue.put`/`take` fail loudly only when they would block), the C1 tree's
documented omissions (a missing class literal is the JVM's catchable
`NoClassDefFoundError`; an omitted superclass ends a walk rather than inventing members),
and the absence of Java stack traces (empty `Throwable.getStackTrace`). Java `equals`
dispatch, interface-default dispatch and the Java-callback paths (`Predicate`,
`BiPredicate`, `Function`, `Consumer`, `spliterator`, `forEach`) live in `rava-interp`
because they re-enter the frame machinery; `rava-vm` keeps the data and the natives that
cannot re-enter. The full auto-configuration path remains the first C3 increment.
