# Testing and evidence: fixtures, gates and reproducible claims

## Question

How are rava's tests and compatibility claims produced, what is committed versus
generated, and what makes a result acceptable evidence?

## Three test layers

| Layer | Runner | What it proves |
| :--- | :--- | :--- |
| Rust unit/integration tests | `cargo test --workspace` (inside `cargo xtask ci`) | The crate contracts and the interpreter/runtime behaviours covered by explicit assertions. |
| Compatibility commands | `rava compat …` | C0/C1 artifacts: target lock, manifest, link surface, metadata diff. |
| Opt-in Spring acceptance | `RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context` | A real `AnnotationConfigApplicationContext` starts and yields the `hello` bean. |

These layers answer different questions. `cargo xtask ci` does not fetch jars, run a
real JDK reflection differential, or claim C0–C4. The Spring test does not replace the
manifest/link/metadata checks.

## Workspace gate

[`xtask/src/main.rs`](../../xtask/src/main.rs) defines:

```console
$ cargo xtask ci
$ cargo fmt --all --check
$ cargo clippy --workspace --all-targets -- -D warnings
$ cargo test --workspace
```

The three steps stop at the first failure. `cargo xtask ci` is the engineering gate: it
must stay green for every code change, including documentation-only changes. It is not a
compatibility gate (see [`compatibility-gates.md`](compatibility-gates.md)).

## Fixture strategy

Fixtures are chosen by what the test must observe:

### Hand-assembled fixtures

Small classes with exact bytecode are built with `ClassBuilder`/`Assembler` from
`rava-classfile` in the test itself. This is preferred when the test needs:

- a precise instruction/exception-table/bootstrap shape (`Point`, `BytecodeProbe`,
  `Boom`/`Catcher`, hand-built invokedynamic call sites);
- an invalid class file or malformed metadata;
- a classpath/jar layout under test.

The bytes are produced in Rust, so the test does not depend on a compiler's choices and
does not need a JDK.

### Compiled Java fixtures

When the point is the **shape javac emits** (bridges, varargs, `Signature`, records,
sealed classes, string-concat `invokedynamic`, lambdas, streams, annotations), the
source and the compiled class files are committed together under
`crates/*/tests/fixtures/…`. Tests read the committed `.class` and need no JDK.

The contract for such a fixture:

1. It is compiled with `javac --release 17` (class-file version 61), and
   `-parameters` where parameter names matter.
2. The source and the compiled classes are both committed.
3. The exact rebuild command is recorded in a `README.md` next to the fixture or in
   the test module header (the older fixtures use the latter).
4. The test asserts observable Java behaviour, not a Rust helper that could fake it.

Examples:

- `crates/classfile/tests/fixtures/java/build.sh` — metadata fixture source and golden dumps.
- `crates/interp/tests/fixtures/{annotations,generics,lambdas,streams,method_flags,lookup_exceptions,invokedynamic}/` — compiled fixtures with local rebuild recipes.
- `crates/cli/tests/fixtures/run/` — directory and stored jar forms of `HelloRun`.
- `crates/cli/tests/fixtures/spring/` — the Spring smoke class, compiled against the
  pinned `compat/jars`; jars themselves are not committed.

### Golden dumps

The metadata model has committed golden text dumps for representative fixtures. A golden
test is intentionally updateable only through an explicit opt-in:

```console
$ RAVA_UPDATE_GOLDEN=1 cargo test -p rava-classfile --test metadata_model
```

After regenerating, review the diff; the environment variable is not a way to silently
accept a regression. The fixture rebuild script also removes the old output before
compiling, so a deleted class cannot linger.

### Jars and classpaths

`HelloRun.jar` is a small `ZIP_STORED` jar committed as a fixture, so the runner and the
jar source are tested without a JDK. The compatibility jars are different: they are
fetched from Maven Central and pinned by `compat/jars.lock`, not committed.

## Compatibility evidence

The compatibility inputs and their owners are:

| Artifact | Generated by | Checked by |
| :--- | :--- | :--- |
| `compat/targets.toml` | hand-maintained target lock | `compat target`, `compat check` |
| `compat/jars.lock` | `compat/fetch-jars.sh --write-lock` | `compat/fetch-jars.sh --check` (sha256), `compat check` (count) |
| `compat/surface/…txt` | `compat manifest` | `compat manifest --check` |
| `stdlib/classes/` | `compat stubs` from the manifest | `compat link-check`, `compat check` |
| `stdlib/c1/classes/` | `compat c1-stubs` from `ct.sym` | `compat metadata --check` |
| `compat/surface/c1-unreferenced.txt` | `compat c1-stubs`/metadata | metadata generation must agree with it |

Typical local sequence, with the pinned JDK and fetched jars:

```console
$ bash compat/fetch-jars.sh                 # once; needs JAVA_HOME + Maven
$ bash compat/fetch-jars.sh --check         # sha256/count/names
$ cargo run -p rava-cli -- compat check     # target/manifest/link/stub determinism
$ cargo run -p rava-cli -- compat metadata --check
```

`compat check` deliberately checks the jar **set/count**, not per-file hashes; the fetch
script's `--check` owns sha256. `compat metadata` needs the host `ct.sym` release-17
view (or `--ct-sym`/`RAVA_CT_SYM`), so it is a local gate too.

The details behind each stage are in
[`compatibility-gates.md`](compatibility-gates.md) and [`c1-metadata.md`](c1-metadata.md);
the trees are described in [`class-loading-and-libraries.md`](class-loading-and-libraries.md).

## Spring acceptance

The Spring test is opt-in because it needs the fetched 35-jar set and a local Spring
classpath:

```console
$ RAVA_SPRING_ACCEPTANCE=1 cargo test -p rava-cli --test spring_context
running 1 test
test spring_annotation_context_starts_and_exposes_the_bean ... ok
```

Without `compat/jars`, or without the environment variable, the test prints a skip and
returns. A skip is **not** evidence of C3. The fixture, classpath and path are documented
in [`spring-context.md`](spring-context.md).

## Adding or changing a test

1. Decide whether the test needs an exact bytecode shape (assemble it) or a
   javac-emitted shape (commit source + `.class` + rebuild recipe).
2. Add the assertion to the owning crate's integration test, with a typed error path
   where the code has one.
3. If a committed fixture is rebuilt, regenerate any golden dump deliberately and review
   the diff.
4. If a compatibility artifact changes (manifest/stubs/target/jars), re-baseline the
   dependent trees and counts, then re-run both `compat check` and
   `compat metadata --check`.
5. Update `PROJECT.md` slice status/log and the owning explanation if the mechanism is
   described there.
6. Run `cargo xtask ci`; for a compatibility or Spring change, also run the local gates.

## Evidence rules

- A claim names the command, the exit code and the artifact/count it produced.
- A skip is not a pass. The Spring opt-in is explicit evidence only when it runs.
- “The test passed” means `cargo test`/the command exits 0, not that a count alone was
  observed.
- A change to a manifest, stub tree, target or jar set is a re-baseline, not a local
  edit; regenerate and review the diff.
- A committed compiled fixture is a binary input, but its source and rebuild command are
  part of the contract. Rebuilding is a deliberate, reviewed change.
- The ledger (`PROJECT.md`) owns dates, counts and slice status; documents link to it
  instead of maintaining a second state table.

## Boundaries

- CI has no JDK and no fetched jars: it runs the workspace tests, and the Spring test
  skips. The local Spring/compat gates are the ones that exercise those inputs.
- There is no full per-class “JDK 17 reflection vs rava reflection” differential; the C1
  gate is a static metadata diff with a documented placeholder boundary.
- `compat check` does not verify jar hashes; `fetch-jars.sh --check` does.
- The workspace test suite is not a fuzzer or a JCStress suite; those are later
  milestones.
- `cargo xtask ci` does not run `compat check`, `compat metadata`, or the Spring test.
- The fixture source and committed `.class` can drift; rebuilding and reviewing is a
  manual discipline, not an automatic CI comparison today.
