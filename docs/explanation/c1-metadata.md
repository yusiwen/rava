# C1 metadata: what the diff compares

## Question

The M2 hand-off says:

> C1 metadata diff is a normalized class-file diff over 1,011 JDK 17 `ct.sym`
> classes; 36 manifest owners do not exist in Java 17, are listed in
> `compat/surface/c1-unreferenced.txt`, and are excluded. It is not a differential
> test against a running JDK 17 reflection implementation.

This document unpacks that sentence: what C1 is, what is compared, why 1,011 and 36,
and what the resulting `differences 0` means.

## What C1 means

C1 is the **Metadata** compatibility level in ADR-0003, not a class, a tree, or a
single test:

| Level | Promise | Gate |
| :--- | :--- | :--- |
| C0 — Link | Every symbolic reference in the observed surface resolves. | `compat check` reports `unresolved 0`. |
| **C1 — Metadata** | Reflection sees the JDK 17 shape for the manifest classes: modifiers, superclass, interfaces, members, descriptors, annotations, generic signatures, records, sealed permits, nestmates and parameter names. | `compat metadata --check` reports `differences 0` for the classes with a reference. |
| C2 — Dynamic | Proxy, `defineClass`, CGLIB, Objenesis, `Lookup`, the declared `Unsafe` subset and generated bytecode verify. | C2 suite exits 0. |
| C3 — Runtime | The observed collections, concurrency, I/O, NIO, networking, charsets, regex, `java.beans`, logging, jars/resources and `ServiceLoader` behave for the exercised paths. | API tests and the Spring context exit 0. |
| C4 — Framework | The reference Boot web application and selected Spring tests run unmodified. | HTTP and Spring suites exit 0. |

The authoritative definitions are in
[ADR-0003](../adr/0003-compatibility-contract.md) and the M2 row of
[`docs/requirements.md`](../requirements.md).

## Inputs and artifacts

There are two distinct class-library trees; confusing them makes the 1,011/36 split
look arbitrary:

| Path | Role | Produced by |
| :--- | :--- | :--- |
| `stdlib/classes/` | M1 synthetic signature stubs used by the C0 link-check. They carry every observed member, but their headers are synthetic. | `rava compat stubs` from the M1 manifest. |
| `stdlib/c1/classes/` | The C1 metadata tree. 1,011 classes are projected from the host JDK's `lib/ct.sym` release-17 signatures; 36 are documented placeholders. | `rava compat c1-stubs`. |
| `compat/surface/spring-boot-3.5.16.txt` | The observed platform surface: classes, fields, methods and interface methods referenced by the 35 pinned jars. | `rava compat manifest`. |
| `compat/surface/c1-unreferenced.txt` | Manifest owners with no release-17 `ct.sym` signature. | `rava compat c1-stubs` / `compat metadata`. |

`ct.sym` is the JDK's historical API-signature archive, the same data `javac
--release 17` consults. Its `.sig` entries are class-file-shaped metadata with no
method bodies. The projection parses each entry with `rava-classfile`, rebuilds the
constant pool at the original indices, sets the class-file version to 61.0 and
re-emits every raw attribute; the writer is in
[`crates/classfile/src/writer.rs`](../../crates/classfile/src/writer.rs), and the
projection/check is in [`crates/cli/src/c1.rs`](../../crates/cli/src/c1.rs).

## The pipeline

1. **Observe the surface.** `rava compat manifest` scans every `.class` entry in the 35
   pinned jars and records platform owners from constant-pool references, member
   descriptors, `Signature` attributes and annotation-encoded types. The current
   closure is 1,047 classes, 177 fields, 3,626 methods and 1,048 interface methods.
2. **Project the C1 tree.** `rava compat c1-stubs` maps each of the 1,047 owners to the
   release-17 `ct.sym` view. 1,011 have a signature; 36 do not and become header-only
   placeholders. The committed tree is 1,047 class files.
3. **Dump and normalize.** The M2.1 metadata model in
   [`crates/classfile/src/metadata/`](../../crates/classfile/src/metadata/) decodes
   class, field, method, record, annotation, type-annotation and signature data. The
   deterministic dump is compared with the same dump of the `ct.sym` reference.
4. **Check C1.** `rava compat metadata --check` reports the counts below and fails on
   the first difference.
5. **Keep C0 green.** `rava compat check` still runs the M1 gate over
   `stdlib/classes/`: manifest reproducibility, link-check and synthetic-stub
   determinism.

## Evidence

From the repository root, with the pinned `compat/jars` fetched:

```console
$ cargo run -p rava-cli -- compat metadata --check
rava compat metadata
  manifest          compat/surface/spring-boot-3.5.16.txt
  c1 stubs          stdlib/c1/classes
  ct.sym            .../lib/ct.sym
  release           17
  classes           1047
  from ct.sym       1011
  unreferenced      36
  fields            1160
  methods           13359
  differences       0
metadata: ok
```

The C0 gate remains separate:

```console
$ cargo run -p rava-cli -- compat check
  target lock + jars  ok (java 17, 35 jars)
  manifest --check    ok (1047 classes, 177 fields, 3626 methods, 1048 interface-methods)
  link-check          ok (1047 classes, 4851 member records, unresolved 0)
  stub determinism    ok (1047 class files byte-identical)
compat check: ok
```

## Why 1,011 and 36

The manifest is an **observed** surface, not “all of Java SE 17”. It includes platform
classes referenced by Spring, including optional/third-party APIs under `javax/`
(and a few `jdk.` internals) that Java 17 does not provide. Those owners are real
manifest targets for C0, but they have no release-17 `ct.sym` signature to compare
against. Examples include JSR-305 annotations, JCache, Moneta, WSDL/Java EE types and
`jdk.internal.vm.annotation.IntrinsicCandidate`; the exact list is
[`compat/surface/c1-unreferenced.txt`](../../compat/surface/c1-unreferenced.txt).

A placeholder is deliberately not a synthetic fake with invented metadata: it carries
its name, `public abstract`, `Object`, version 61 and a marker `SourceFile`, and it is
excluded from the C1 diff. The generator fails if the archive and the committed list
disagree, so the exception list cannot silently grow.

## What is normalized

The check is normalized, but narrowly:

- ordering and formatting are deterministic;
- the class-file version line is normalized (the host `ct.sym` stores 69; the committed
  stub is 61);
- placeholders are excluded;
- every other metadata line — flags, superclass, interfaces, members, descriptors,
  annotations, signatures, records, sealed permits, nests, parameter names and raw
  attribute names/lengths — is compared unmodified.

This differs from a **running JDK 17 reflection diff**. A live differential would call
`Class.getDeclaredFields()`, `getDeclaredMethods()`, `getAnnotations()`,
`getGenericSuperclass()`, `getParameters()` and related APIs on both VMs, normalize
identity/ordering and compare the observed objects. The M2.23 Spring smoke exercises a
narrow runtime reflection path, but there is no full per-class live differential.

## What “differences 0” proves

It proves that:

- the projection did not lose the metadata present in the `ct.sym` signature;
- the committed C1 tree does not drift from its reference;
- the 1,011 classes with a reference have the same static metadata shape;
- the 36 exceptions are explicit and reviewable.

It does **not** prove that:

- every reflection call in rava matches JDK 17 semantics;
- annotation proxy identity/equality, generic `Type` identity, parameter-name edge
  cases or module/nestmate behaviour are fully JDK-identical;
- the 36 placeholder owners have C1 metadata;
- the C1 gate has been exercised for every manifest class.

If the project later decides that C1 means “every manifest class plus a live JDK 17
differential”, this boundary must be reopened and the 36 placeholders re-scoped. The
current M2 claim is a qualified pass under the documented boundary.
